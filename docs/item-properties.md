# Дадатковыя ўласцівасці наменклатуры

Статус: Review. Галіна: `feat/catalog-item-properties`. Бізнес-прыёмка яшчэ не праведзена.

## Паводзіны

Карыстальнік з `MasterData.Manage` наладжвае ўласцівасці канчатковага класа і ўводзіць значэнні для наменклатуры і партый. `MasterData.View` дазваляе прагляд. Групы не маюць уласцівасцяў; наследаванне не выкарыстоўваецца. Значэнні неабавязковыя; адсутнасць адрозніваецца ад нуля і «Не».

Тыпы: лік (0–6 знакаў), тэкст (1–4000 сімвалаў), адзін варыянт з уласнага спіса, Так/Не, дыяпазон з дзвюма ўключнымі межамі. Для дыяпазону наладжваюцца дапушчальныя мінімум, максімум і дакладнасць. Лікі захоўваюцца як decimal(24,6), праз JSON перадаюцца радкамі без страты дакладнасці. Лішнія значныя дзесятковыя знакі адхіляюцца без акруглення.

Узгоднена карыстальнікам: сярэдняе значэнне ў картцы ўводзіцца ўручную; патрэбны мінімальны ўлік партый. Партыя мае нумар у межах item, дату прыходу і тэкставую спасылку на дакумент. Пры стварэнні капіююцца значэнні толькі ўласцівасцяў з прыкметай «Уласцівасць партыі». Копія захоўваецца незалежна; пазнейшая змена item яе не змяняе. Партыі не ствараюць складскіх рухаў і не з'яўляюцца праведзенымі дакументамі прыходу.

## Цэласнасць

- Вызначэнне належыць аднаму класу. Пакуль ёсць захаваныя значэнні, нельга змяніць тып, абмежаванні, прыкмету партыі або выдаліць/пераназваць варыянты спіса; можна дадаць варыянты, пераназваць уласцівасць і дэактываваць яе.
- Дэактывацыя захоўвае ранейшыя значэнні для прагляду.
- Змена класа item з захаванымі значэннямі або партыямі забаронена, каб не страціць гісторыю.
- Захаванне набору значэнняў атамарнае; RowVersion уладальніка выяўляе канкурэнтнае рэдагаванне. Канфлікт патрабуе перазагрузкі.
- Паўторнае PUT не стварае дубляў значэнняў; паўторнае стварэнне партыі з тым жа нумарам або ўласцівасці з тым жа кодам дае 409.
- Audit-палі захоўваюць аўтара і час стварэння/апошняй змены. Выдаленне партый і фізічнае выдаленне налад праз API не прадугледжваюцца.

## План рэалізацыі і праверкі

1. Domain: мадэлі і праверка пяці тыпаў значэнняў; xUnit для межаў і дакладнасці.
2. EF Core: асобныя табліцы вызначэнняў, варыянтаў, значэнняў item, партый і значэнняў партыі; FK Restrict, унікальныя індэксы, новая міграцыя без змены існуючых даных.
3. Application/Infrastructure/API: кантракты, сэрвіс, правы, атамарнасць і канкурэнцыя.
4. Angular: наладкі ўласцівасцяў класа, значэнні item і партыі; формы адпаведнага тыпу, лакалізацыя і памылкі API.
5. Праверкі: domain tests, build, lint/unit/i18n, pending model; SQL Server Testcontainers пры наяўнасці Docker. Бізнес-прыёмка асобная ад build.

## Уплыў на базу

Міграцыя дадае пустыя табліцы; backfill не патрэбны. Існуючая база аўтаматычна не абнаўляецца. Адкат пасля пачатку выкарыстання выдаліў бы новыя даныя і патрабуе асобнай аўтарызацыі і рэзервовай копіі.


## Структура базы

| Табліца | Прызначэнне і ключы |
| --- | --- |
| ItemPropertyDefinitions | Наладкі; FK CatalogItemClassId; унікальныя ClassId + Code; RowVersion |
| ItemPropertyOptions | Варыянты спіса; FK PropertyId; унікальныя PropertyId + Label |
| CatalogItemPropertyValues | Значэнні item; PK CatalogItemId + PropertyId; Number, Upper, Text, Boolean або OptionId |
| CatalogItemBatches | Партыі; FK CatalogItemId; унікальныя CatalogItemId + Number; ReceiptDate, ReceiptReference, RowVersion |
| BatchPropertyValues | Значэнні партыі; PK BatchId + PropertyId; тыя ж тыпізаваныя палі |

Composite FK (PropertyId, OptionId) забараняе варыянт чужой уласцівасці. Check constraints правяраюць форму значэння і наладкі. Належнасць класу і прыкмета партыі правяраюцца сэрвісам у serializable-транзакцыі. FK выкарыстоўваюць Restrict. Не больш за 500 уласцівасцяў на клас і 500 варыянтаў на спіс.

## API

Усе маршруты пачынаюцца з `/api`. GET патрабуе MasterData.View, POST/PUT — таксама MasterData.Manage.

| Метад і маршрут | Паводзіны |
| --- | --- |
| GET catalog-item-classes/{classId}/properties | Усе вызначэнні класа, у тым ліку неактыўныя |
| POST catalog-item-classes/{classId}/properties | Стварэнне вызначэння |
| PUT catalog-item-classes/{classId}/properties/{id} | Змена вызначэння з RowVersion |
| GET/PUT catalog-items/{itemId}/properties | Прагляд/змена сярэдніх значэнняў |
| GET catalog-items/{itemId}/batches?page=1 | Спіс партый, 50 на старонку |
| POST catalog-items/{itemId}/batches | Новая партыя і атамарнае капіяванне сярэдніх значэнняў |
| PUT catalog-items/{itemId}/batches/{id} | Рэдагаванне нумара, даты, спасылкі з RowVersion |
| GET/PUT catalog-items/{itemId}/batches/{batchId}/properties | Прагляд/змена значэнняў канкрэтнай партыі |

GET значэнняў вяртае `rowVersion`, `definitions`, `values` і для партыі яе актуальныя рэквізіты `batch`.
PUT змяняе толькі перададзеныя ўласцівасці; адсутныя ў payload не выдаляюцца.
Для ачысткі перадаецца `propertyId` з усімі значэннямі null. Неактыўныя ўласцівасці даступныя толькі для прагляду.
Кожны PUT патрабуе актуальную RowVersion; паўтор з ранейшай версіяй дае 409 нават пры аднолькавым payload.

Прыклад значэння дыяпазону:

```json
{
  "rowVersion": "<version from GET>",
  "values": [
    { "propertyId": "<property GUID>", "number": "100.00", "upper": "15000.00" }
  ]
}
```

Новыя варыянты спіса перадаюцца як `{ "id": null, "label": "Назва" }`, існуючыя — з іх GUID.
Памылкі: 400 — невалідныя значэнні, 403 — недастаткова правоў, 404 — неіснуючы/чужы ўладальнік, 409 — дублі або канкурэнтная змена.
Audit адлюстроўвае стварэнне і апошняе рэдагаванне; поўны журнал усіх рэвізій значэнняў не дадаваўся.

## Інтэрфейс і запуск

1. Адкрыць «Адміністраванне → Дадатковыя ўласцівасці», выбраць тып наменклатуры і канчатковы клас.
2. Дадаць уласцівасць, выбраць тып і адпаведныя абмежаванні.
3. Выбраць захаваны item → «Уласцівасці і партыі» → увесці сярэднія значэнні.
4. «Дадаць партыю» → нумар, дата, спасылка → захаваць → пры патрэбе змяніць скапіяваныя значэнні.
5. Неактыўныя ўласцівасці захоўваюцца для прагляду. Форма папярэджвае аб страце незахаваных змен; пасля 409 уведзеныя даныя застаюцца ў форме.

Створаная міграцыя `20260921191147_AddItemPropertiesAndBatches`. Рабочая база не змянялася. Перад выкарыстаннем патрэбныя праверка на SQL Server і прымяненне міграцыі паводле `docs/local-development.md`, затым перазапуск API. Канфігурацыя і правы роляў не змяняліся.
